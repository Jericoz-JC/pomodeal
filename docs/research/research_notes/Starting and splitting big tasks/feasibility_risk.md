# Feasibility and risk brief: starting and splitting big tasks on the Pomodeal stack (skeptic-engineer notes)

Researched 2026-11-08. "Verified" means read from a primary source today; "knowledge, verify" means from training data and not confirmed in this pass. Platform facts for iOS move fast; re-check anything marked uncertain before building on it.

## 1. Web Push, badging and wake lock on installed PWAs (iOS and Android), late 2026

### Takeaway
Push on iOS works only for a Home Screen-installed web app on iOS 16.4+, and the iOS story got materially better with Declarative Web Push in iOS 18.4 (no service worker required, no silent-push penalties, built-in `app_badge`). Android push is close to native but subject to Doze batching. Nobody publishes delivery-rate numbers; developer forums still report iOS push "not working" cases in 2026, so the timer must never depend on a push arriving.

### Cited Findings
- iOS web push requires iOS 16.4+ and "the PWA must be installed to the home screen first"; no automatic install prompt exists on iOS; Badging API works on iOS 16.4+ installed apps — [MagicBell guide, updated 2026-03-20](https://www.magicbell.com/blog/pwa-ios-limitations-safari-support-complete-guide)
- Background Sync, Periodic Background Sync and Background Fetch are not supported on any iOS version; the suggested workaround is to sync on the `online` event and on visibility change — [MagicBell guide](https://www.magicbell.com/blog/pwa-ios-limitations-safari-support-complete-guide)
- Same source claims a 7-day cache expiry and 50 MB storage cap on iOS PWAs, and that iOS 17.4 removed standalone PWAs, push and badges in the EU — [MagicBell guide](https://www.magicbell.com/blog/pwa-ios-limitations-safari-support-complete-guide). Knowledge, verify: Apple announced in March 2024 that it would keep Home Screen web apps in the EU after all, and Apple has stated that installed Home Screen web apps are exempt from the 7-day script-writable-storage eviction. Treat the MagicBell EU/eviction claims as contested.
- Declarative Web Push (Apple): notifications display from a JSON payload with a top-level `"web_push"` key and a `"notification"` object (non-empty `"title"`, required `"navigate"` URL opened on tap); a service worker is optional; optional `"app_badge"` member updates the badge on Home Screen web apps; "Service worker failures carry no penalty, and the message is still displayed"; browsers do not apply silent-push penalties because a user-visible notification always appears; testable on iOS 18.4 / iPadOS 18.4 / macOS 15.5 beta — [WebKit blog: Meet Declarative Web Push](https://webkit.org/blog/16535/meet-declarative-web-push/)
- Declarative Web Push shipped March 2025 in iOS 18.4; macOS followed in 15.5 / Safari 18.5; works inside Home Screen web apps — [aimtell, State of Declarative Web Push 2026](https://aimtell.com/blog/state-of-declarative-web-push-2026); [progressier demo page](https://progressier.com/pwa-capabilities/declarative-web-push)
- Subscribing still requires an explicit user gesture (`window.pushManager.subscribe()` with `userVisibleOnly: true`) — [WebKit blog](https://webkit.org/blog/16535/meet-declarative-web-push/)
- Notification action buttons on iOS: sources conflict. MagicBell lists "notification actions" as working; another vendor says Safari lacks support for images or action buttons in web notifications — [MagicBell](https://www.magicbell.com/blog/pwa-ios-limitations-safari-support-complete-guide); contradicted by [EngageLab, Safari notifications](https://www.engagelab.com/de_DE/blog/safari-notifications). Knowledge, verify: `Notification.maxActions` has historically been 0 on Safari, so plan for no action buttons on iOS.
- Reliability anecdotes persist: a February 2026 report of a Next.js PWA whose push works on Android/Chrome but not iOS Home Screen; an Apple developer forum thread asking for "more reliable" alternatives — [Reddit snapshot 2026-02-18](https://reddit.sentinel-team.org/posts/1r7cdbs/snapshots/2026-02-18T00%3A30%3A19.469815Z); [Edana, March 2026](https://edana.ch/en/2026/03/19/push-notifications-on-web-applications-pwa-is-it-really-reliable-on-ios-and-android/) which says Android PWA push is "complete and comparable to native"
- Android delivery: FCM normal-priority messages are "batched together and delivered opportunistically when the device is in Doze mode"; high priority "attempts to deliver ... immediately" and can wake the device, but vendors report that even high-priority delivery "might be deferred to a periodic maintenance window" in Doze; sending too many high-priority messages can get you deprioritized — [Firebase message priority](https://firebase.google.com/docs/cloud-messaging/customize-messages/setting-message-priority); [Pushwoosh](https://help.pushwoosh.com/hc/en-us/articles/27979811724701-What-does-the-android-delivery-priority-parameter-do-for-Android-push-notifications); [OneSignal, notifications delayed](https://documentation.onesignal.com/docs/notifications-delayed)
- Web Push protocol expresses urgency separately from FCM priority via the `Urgency: high` header — [Firebase docs example](https://firebase.google.com/docs/cloud-messaging/customize-messages/setting-message-priority); how Chrome on Android maps that header to Doze handling was not documented in anything I found.
- Screen Wake Lock: supported in iOS Safari 16.4+, but broken in installed Home Screen apps until Apple fixed it in iOS 18.4 (released 2025-03-31) — [progressier wake lock](https://progressier.com/pwa-capabilities/screen-wake-lock); [web-features explorer](https://web-platform-dx.github.io/web-features-explorer/features/screen-wake-lock); an older status page still says it does not work in installed apps, which looks outdated — [whatpwacando.today](https://whatpwacando.today/wake-lock)

### Inferences
- Minimum bar for the 2-minute heads-up and block-end pushes: iOS 16.4 installed (classic push) and iOS 18.4 installed (declarative). Sending the declarative JSON shape is backwards compatible, so one payload format serves both; older iOS falls back to the service worker handler.
- Because iOS probably has no action buttons, the "negotiate from the notification" idea (Extend 10 / Stop now on the banner) is Android-only. The tap must open the app to a negotiation screen; `navigate` in the declarative payload can carry a deep link like `/deal/<id>?at=end`.
- Not installed on iOS = no push, no badge, no standalone. Push on a Safari tab is impossible, so the onboarding step "add to Home Screen" is a prerequisite for every reminder feature, and the share-sheet install flow is manual and unfamiliar to most users.
- A 2-minute heads-up delivered by push can arrive late (Doze) or not at all (iOS edge cases). The block end should always be enforced client-side from `startedAt + duration`; push is a convenience layer.
- Wake lock is now viable for the active-timer screen on iOS 18.4+ installed; request it on focus start, release on break, re-request on `visibilitychange`.

### Gaps
- No primary-source delivery-rate or latency data for iOS web push or Declarative Web Push. All reliability claims are vendor or forum anecdotes.
- Whether the EU Home Screen web app behavior described by MagicBell is current. Matters little for a closed beta unless any testers are in the EU.
- Current `Notification.maxActions` on iOS 26 Safari; not verified this pass.

## 2. Convex: scheduled functions for block boundaries and multi-day reminders, actions for the Claude API

### Takeaway
Convex scheduling is a good fit: one scheduled function per boundary, cancel-and-reschedule on each negotiation, stored in the database and durable across restarts, with limits (1,000,000 outstanding, 1,000 scheduled per mutation) far above beta needs. The real constraints are the free tier's 8 concurrent scheduled jobs and the fact that actions are never retried, so every external call needs the mutation -> schedule action -> mutation pattern with an idempotency check.

### Cited Findings
- `ctx.scheduler.runAfter(delayMs, fn, args)` and `runAt(timestampMs, fn, args)`; scheduled functions are stored in the database and can be scheduled "minutes, days, or months ahead"; scheduling survives downtime and restarts — [Convex scheduled functions](https://docs.convex.dev/scheduling/scheduled-functions)
- Each scheduled function is a document in `_scheduled_functions` with `name`, `args`, `scheduledTime`, `completedTime`, `state` (Pending, InProgress, Success, Failed, Canceled); results kept 7 days — [Convex scheduled functions](https://docs.convex.dev/scheduling/scheduled-functions)
- `ctx.scheduler.cancel(id)`: not run if it hasn't started; if it has started it keeps running but anything it schedules will not run. No reschedule API; cancel and schedule again — [Convex scheduled functions](https://docs.convex.dev/scheduling/scheduled-functions)
- Scheduling from a mutation is atomic with the mutation's commit; from an action it is not. Scheduled mutations run exactly once (Convex retries internal errors); actions "run at most once and fail permanently on transient errors", are never auto-retried — [Convex scheduled functions](https://docs.convex.dev/scheduling/scheduled-functions)
- Auth context is not propagated to scheduled functions; pass the user id as an argument — [Convex scheduled functions](https://docs.convex.dev/scheduling/scheduled-functions)
- Limits: 1,000 functions scheduled per mutation; 4 MiB per scheduled call's args, 16 MiB total per mutation; up to 1,000,000 outstanding scheduled functions; concurrent scheduled jobs: 8 on Free/Starter (S16), 256 on Professional (S256); scheduled executions count toward function-call totals — [Convex limits](https://docs.convex.dev/production/state/limits)
- Function calls: Free 1,000,000/month with hard caps; Starter 1,000,000 included then $2.20 per extra 1,000,000; Professional 25,000,000 included then $2 per 1,000,000. Action compute: Free 20 GB-hours/month; Starter 20 GB-hours then $0.33/GB-hour; Professional 250 GB-hours then $0.30/GB-hour — [Convex limits](https://docs.convex.dev/production/state/limits)
- Actions: default Convex runtime has no cold starts, 64 MiB, `fetch` works, not all npm packages supported; Node runtime (`"use node"`) 512 MiB, 10-minute timeout (limits page says 30 min for Convex runtime, 10 min for Node); concurrent actions 64 on S16 — [Convex actions](https://docs.convex.dev/functions/actions); [Convex limits](https://docs.convex.dev/production/state/limits)
- "Calling an action directly from a client is an anti-pattern in most cases." Recommended: client calls a mutation that records intent and schedules an internal action with `runAfter(0, ...)`; the action calls the external API then runs a mutation to store the result; the first mutation can prevent duplicate runs. Await all promises inside actions — [Convex actions](https://docs.convex.dev/functions/actions)
- To retry a failed action, schedule a mutation that checks whether the outcome happened and, if not, schedules the action again — [Convex scheduled functions](https://docs.convex.dev/scheduling/scheduled-functions)
- Cron jobs are static in `convex/crons.ts` (`interval`, `cron`, `hourly/daily/weekly/monthly`); at most one run of each job executes at a time, long runs cause skipped runs; avoid minute 0 of the hour (busiest), and the `@convex-dev/no-top-of-hour-crons` lint exists — [Convex cron jobs](https://docs.convex.dev/scheduling/cron-jobs). Crons cannot be created per user at runtime (not described anywhere; all examples are static).
- Project's own Convex guidelines: never read the wall clock in a query; `Date.now()` is fine in mutations and actions; for bounded-parallel or retried work use `@convex-dev/workpool` and "retry only idempotent actions" — local file `convex/_generated/ai/guidelines.md` lines 82 and 90
- Rate limiting component `@convex-dev/rate-limiter` (v0.3.2) supports token bucket and fixed window with a per-user `key`; transactional so it never over-grants under concurrency — [README](https://cdn.jsdelivr.net/npm/@convex-dev/rate-limiter@0.3.2/README.md); community guidance pairs a per-user limit with a global cap so one user cannot drain the provider budget — [community skill](https://skills.cat/skills/sstobo/convex-skills/convex-agents-rate-limiting)

### Inferences
- Load math for the beta: 2 scheduled functions per block (heads-up at T-2 min, end at T). 100 users x 6 blocks/day x 2 = 1,200 scheduled runs/day, about 36,000/month, plus the mutations that scheduled them. That is under 4% of the free tier's 1,000,000 calls. Multi-day plans add one "next segment is due" nudge per plan per day, negligible.
- The 8-concurrent-scheduled-jobs limit on Free is the one that can bite: if a Node action that sends a push takes 1 to 2 s (cold start plus VAPID signing plus fetch), a burst of 50 boundaries in the same second queues for 6 to 12 s. Blocks start at arbitrary times so bursts are rare, but any "everyone starts at 7 pm" room feature would create them. Keep the boundary mutation tiny and push the slow part (web push HTTP call) into a separate action.
- Reschedule pattern that avoids cancel races: store `scheduledFnId` and a `version` integer on the block document. Each negotiation increments `version`, cancels the old id, schedules a new one with `{blockId, version}`. The scheduled function first reads the block and returns if `version` does not match. This makes a missed cancel harmless and the function idempotent.
- Multi-day reminders: do not create one scheduled function per plan per future day. Keep one daily cron at an off-peak minute that queries plans with `nextDueAt <= now` and schedules per-user push actions, or use `runAt` for the single next nudge and reschedule after it fires. Either way, auth must be passed explicitly.
- Web Push sending from Convex needs VAPID signing. Knowledge, verify: the `web-push` npm package needs the Node runtime (`"use node"`), which adds cold starts; a WebCrypto-based signer can run in the default runtime. Either way the Claude call and the push call should live in internal actions scheduled from mutations, never called from the client.

### Gaps
- Timing precision of scheduled functions (how late a `runAt` can fire under load) is not documented. Assume seconds, not milliseconds, and never show a scheduled push as the source of truth.
- Professional plan price was not fetched this pass (knowledge: about $25/member/month; verify on convex.dev/pricing).

## 3. Claude API for task breakdown: models, prices, latency, structured output, cost per user, privacy, rate limiting

### Takeaway
Haiku 5.5 at $0.10 input / $0.50 output per MTok makes a breakdown cost well under a tenth of a cent, so 5 breakdowns a day is about $0.05 to $0.07 per user per month even without caching; Sonnet 5.5 is roughly 15 to 20 times that, still under $1.50. Structured outputs are GA and solve the "return JSON steps" problem cleanly. The non-trivial costs are privacy (assignment text leaves the app, 30-day retention by default) and the product risk that an AI breakdown becomes a thing to argue with rather than a start button.

### Cited Findings
- Current lineup and base prices per MTok (input / output): Haiku 5.5 $0.10 / $0.50 for prompts up to 100k tokens ($0.50 / $2.50 above that); Sonnet 5.5 $2 / $10; Opus 5.5 $4 / $20; Fable 5.1 $10 / $50. Haiku 4.5 is $1 / $5 — [Claude pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- Comparative latency: Haiku 5.5 "Fastest", Sonnet 5.5 "Fast", Opus 5.5 "Moderate"; Haiku 5.5 is positioned "for high-volume, latency-sensitive tasks such as classification, extraction, and routing"; all current models 1M context, 128K max output; API ids `claude-haiku-5-5`, `claude-sonnet-5-5`, `claude-opus-5-5`; retirement not sooner than October 7, 2027 for Haiku 5.5 — [Models overview](https://platform.claude.com/docs/en/about-claude/models/overview)
- Thinking is "Adaptive" on Haiku 5.5 and Sonnet 5.5 (default effort medium and high respectively); the Models API reports Sonnet 5.5 does not accept `thinking: {type: "disabled"}` but does accept `between_tools` — [Models overview](https://platform.claude.com/docs/en/about-claude/models/overview)
- Models from 4.7 on use a tokenizer that produces about 30% more tokens for the same text — [Claude pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- Prompt caching: 5-minute cache write 1.25x base, 1-hour write 2x, cache read 0.1x base (0.05x on Opus 5.5 and Sonnet 5.5, so $0.10/MTok on Sonnet 5.5); Haiku 5.5 cache read $0.01/MTok; automatic caching via a single top-level `cache_control` — [Claude pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- Batch API gives 50% off both input and output (Sonnet 5.5 $1 / $5) but is asynchronous, so not useful for an interactive breakdown — [Claude pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- Structured outputs are GA (no beta header): `output_config.format = {type: "json_schema", schema}` constrains the text response; `strict: true` on tool definitions validates tool inputs; TypeScript helper `zodOutputFormat()`; supported on claude-haiku-5-5, claude-sonnet-5-5, claude-opus-5-5 and others — [Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)
- Schema limits: `additionalProperties: false` required on objects; no `minimum`/`maximum`, no `minLength`/`maxLength`, `minItems` only 0 or 1, no recursive schemas; up to 24 optional parameters; "Schema is too complex" errors possible; the compiled grammar is cached 24 hours; changing `output_config.format` invalidates the prompt cache; an extra system prompt is injected (more input tokens); `stop_reason` of `refusal` or `max_tokens` can yield non-conforming output — [Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)
- Data handling: commercial terms prohibit training on customer content; API inputs and outputs are deleted within 30 days by default except for usage-policy enforcement and legal holds; zero data retention is by arrangement with sales, per organization; prompt caching and structured outputs "may override the zero data retention controls" (the JSON schema is cached up to 24 hours); Fable/Mythos models require 30-day retention — [API and data retention](https://platform.claude.com/docs/en/manage-claude/api-and-data-retention); [Anthropic privacy center, ZDR exceptions](https://privacy.claude.com/en/articles/8956058-i-have-a-zero-data-retention-agreement-with-anthropic-what-are-the-exceptions)

### Inferences
- Cost model per breakdown (assumptions: 1,500-token system prompt and few-shot, 300-token user task text, 500-token JSON output of 6 to 10 segments; the newer tokenizer is already roughly baked into these round numbers):
  - Haiku 5.5, no caching: input 1,800 x $0.10/M = $0.00018; output 500 x $0.50/M = $0.00025; about $0.00043 per call. 5/day x 30 days = 150 calls = about $0.065 per user per month. With the system prompt cached, about $0.05. 100 beta users at 5/day: about $5 to $6.50 a month. At a realistic 0.5/day: under $1 a month for the whole beta.
  - Sonnet 5.5, no caching: $0.0036 + $0.005 = about $0.0086 per call; 150 calls = about $1.29 per user per month. With a 1-hour cached system prompt (300 fresh input tokens at $2/M + 1,500 cache-read at $0.10/M + output): about $0.0058 per call, about $0.87 per user per month.
  - Opus 5.5: about $0.017 per call, about $2.60 per user per month at 5/day. Not justified for this task.
  - Hidden multiplier: adaptive thinking tokens are billed as output. If Sonnet 5.5 spends 1,000 thinking tokens per call that doubles the output cost; set `effort` low and keep the schema small. Haiku 5.5 with low effort is the default choice; promote to Sonnet 5.5 only if evals show Haiku's segment quality is bad.
- Latency: no official numbers published; a 500-token output at Haiku speeds is plausibly 2 to 5 s end to end from a Convex action, longer for Sonnet with thinking. That is long enough that the UI must not block the "Start" button on the AI: show a one-segment default immediately and let the breakdown arrive reactively via the mutation that stores it (Convex's reactivity makes this free).
- Privacy posture that avoids a ZDR negotiation: send only what the breakdown needs (task title, type, rough size, deadline relative to now, user's own notes), strip emails/names/course codes client-side with a simple regex pass, never send pasted assignment PDFs, and store only the user-edited segment list, not the raw prompt or raw model output. Each new stored field (task title, segment titles, segment durations, AI-used flag) goes into `docs/specs/006-privacy-inventory.md` in the same change. Sending free text about a student's coursework to a third party is a new category for the privacy inventory and should be opt-in per request, not a default.
- Rate limiting: a per-user token bucket of roughly 10 breakdowns/day with a global cap of a few hundred/day covers the beta and makes the worst-case bill bounded (300 calls/day x $0.0086 Sonnet = $2.58/day). Use `@convex-dev/rate-limiter` keyed by user id inside the mutation that schedules the action, so an over-limit request never reaches the Claude API.
- Breakdown failure modes to design for: refusal stop_reason, max_tokens truncation, and schema-valid-but-useless output (ten segments of "work on essay"). Always offer the no-AI path: "one block of 45, then decide" is a valid breakdown and costs nothing.

### Gaps
- Claude API per-organization rate limits by usage tier were not fetched this pass; for a beta the per-user limiter above is the binding constraint anyway.
- No published latency numbers for Haiku 5.5 or Sonnet 5.5 time-to-first-token or tokens per second.
- Whether Pomodeal's volume qualifies for ZDR at all (it is "by arrangement via sales"); a closed beta almost certainly operates under default 30-day retention.

## 4. iOS Shortcuts "app opened" automations in iOS 18/26+

### Takeaway
"Run Immediately" exists for the App trigger since iOS 17, but Apple requires such automations to always post a notification banner, users report intermittent prompting and silent failures across iOS 18.x, and the open-source one sec alternative needed an iOS 26 App Intents change to stop infinite loops. The mechanism is usable for a motivated minority who will set it up by hand, not as a product pillar.

### Cited Findings
- Most automation types gained "Run Immediately" in iOS 17; Apple "requires that these automation types always notify you" and hides the "Notify When Run" toggle when Run Immediately is chosen — [Matthew Cassinelli](https://matthewcassinelli.com/automations-run-immediately-shortcuts-notifications)
- Apple's App trigger offers "Is Opened" and "Is Closed" conditions — [Apple Shortcuts User Guide](https://support.apple.com/en-gu/guide/shortcuts/apde31e9638b/ios)
- iOS 18 reports: an automation "set to run immediately" began asking for confirmation again; automations not firing on a locked device; "There was a problem running the automation" errors since iOS 18 beta 2; in one hourly test only 6 of 18 runs succeeded; low battery or Low Power Mode can delay or skip automations — [MacRumors thread](https://forums.macrumors.com/threads/automation-set-to-run-immediately-keeps-asking-for-confirmation-since-18-2.2445766); [MacRumors thread](https://forums.macrumors.com/threads/automation-control-shortcuts-failing.2430032); [Apple Community](https://discussions.apple.com/thread/255820198); [Apple Community](https://discussions.apple.com/thread/256063789)
- one sec (the commercial app built on this exact pattern) documents that automations do not trigger for about two minutes after boot, require the "Original App to be Opened" parameter on each automation, and ships a debug banner explaining why an automation did not trigger — [one sec troubleshooting](https://tutorials.one-sec.app/troubleshooting/iphone-or-ipad-app-does-not-work-as-expected); one sec also has a help article titled "Shortcut Automations are Slow [iOS]" — [one sec feedback](https://feedback.one-sec.app/help/articles/7569907-shortcut-automations-are-slow-ios)
- A developer building an open-source one sec alternative says Apple added `.foreground(.dynamic)` to App Intents in iOS 26, which let them break the Shortcuts infinite loop (open Instagram -> open app -> reopen Instagram -> trigger again) — [DEV Community post](https://dev.to/eliguzz/building-an-open-source-one-sec-alternative-breaking-the-shortcuts-infinite-loop-thanks-to-ios-26-ka4). This is a native App Intents API, not available to a PWA.
- Bluetooth and Wi-Fi triggers run automatically in iOS 26; repeated prompts usually mean "one of the selected actions still requires confirmation" — [switchingtomac guide](https://www.switchingtomac.com/advanced-iphone-shortcuts-ai-automation/) (secondary source)
- A single unverified source says iOS 27.2 adds "upgrades to the ... App triggers" without detail — [itechify](https://itechify.com/?p=11810)

### Inferences
- The Intercept flow for a PWA is: Shortcuts "Instagram is opened" -> Run Immediately -> "Open URL https://pomodeal.app/intercept?app=instagram" (or "Get Contents of URL" POST to a Convex HTTP action). Knowledge, verify: Shortcuts' Open URL opens Safari, not the Home Screen web app, and Safari and the installed web app have separate storage on iOS, so the user may land in a logged-out Safari tab (WorkOS session cookie not shared). The POST-to-HTTP-endpoint path avoids this but needs a per-user secret token embedded in the shortcut (a new privacy-inventory item) and gives no UI.
- The loop problem (Pomodeal sends the user back to Instagram, which re-triggers the automation) has no clean fix for a web app; one sec's fix is native. Mitigation: the Convex endpoint records `lastInterceptAt` and the shortcut checks a "Get Contents of URL" response before opening Pomodeal, or the automation is paired with a 5-minute "app-switching interval" the way one sec does.
- Every intercept shows a Shortcuts banner on top of whatever else happens. That is Apple's design, not a bug, and it undercuts the "calm, no-nag" voice unless the copy embraces it.
- Expect a long tail of "it stopped working after the iOS update" support. This is acceptable for a hand-installed power-user feature and unacceptable as a default onboarding step.

### Gaps
- No Apple release notes found describing iOS 26 or 27 changes to the App trigger's prompting or reliability; the only iOS 27.2 mention is a single unverified article.
- No measured success rate for "app opened" automations; forum numbers (6 of 18) are single anecdotes.

## 5. Offline-first for a server-time timer, clock skew, flaky campus wifi

### Takeaway
Because the timer is pure arithmetic over `startedAt + duration`, the client can keep counting with no network; what breaks offline is everything that needs a round trip (negotiation writes, scheduled boundaries, push, auth refresh). The Convex client buffers mutations in memory while disconnected but not across an app kill, so a negotiation made in a dead zone can be lost if the OS evicts the PWA before wifi returns.

### Cited Findings
- Convex staff on Discord: the client "will hold onto mutations for at least a week to send up the next time it has service"; mutations are "stored in memory" and a "You have unsaved work" alert appears if the tab closes before confirmation; a user asked whether the queue survives app kills and got no answer in the thread — [Convex Discord questions](https://discord-questions.convex.dev/m/1242127900052819998); [Convex Discord questions](https://discord-questions.convex.dev/m/1328729179113525351)
- Convex guidance: do not read the wall clock in a query; pass current time as an argument or materialize time state with scheduled mutations; `Date.now()` is fine in mutations and actions — local `convex/_generated/ai/guidelines.md` line 90
- iOS PWAs have no Background Sync of any kind; sync on `online` and `visibilitychange` — [MagicBell guide](https://www.magicbell.com/blog/pwa-ios-limitations-safari-support-complete-guide)
- iOS Safari can evict cached data when storage is low and clearing Safari history clears PWA caches — [MagicBell guide](https://www.magicbell.com/blog/pwa-ios-limitations-safari-support-complete-guide)

### Inferences
- Clock skew: Convex gives no server-time query, and queries cannot read the clock. Have the "start block" mutation return `serverNow` (`Date.now()` inside the mutation) alongside `startedAt`; the client stores `offset = serverNow - Date.now()` and renders from corrected time. Phones are usually within a second of NTP, but a skewed laptop can be minutes off, which would make the client's ring and the server's scheduled push disagree. One offset measurement per session is enough; re-measure after `visibilitychange`.
- The scheduled functions fire on server time; the client's local end-of-block transition must be computed with the same corrected clock or the ring will hit zero before or after the push lands.
- vite-plugin-pwa precaching keeps the shell loading offline, so the active ring survives a wifi drop. Risk, knowledge-based: WorkOS AuthKit access tokens are short-lived; if a refresh is attempted offline the app may show a sign-in wall mid-block. The shell should treat "token refresh failed because offline" as "keep showing the timer read-only" rather than redirecting.
- Idempotency: with ambiguous network failures a mutation may be retried; negotiations should carry a client-generated `dealId`/`version` so a replayed "extend 10 minutes" does not extend twice (same `version` check as the scheduler pattern in section 2).
- Multi-day plans need nothing special offline: the plan document is already in the client's query cache; the only online-only action is marking a segment done, which is a small idempotent mutation that can wait in the buffer.

### Gaps
- Whether the Convex JS client's buffered mutations survive a PWA being killed by iOS (almost certainly not; nothing in the client type definitions suggests persistence, but not confirmed).
- No measurements of WebSocket reconnect behavior on captive-portal campus wifi.

## 6. Evidence check: do AI task breakdown and gamified progress improve completion or retention?

### Takeaway
No randomized trial of AI-generated task breakdowns on completion exists in what I found. The best-supported adjacent mechanism is implementation intentions ("when X, I will do Y"), whose effect has shrunk from d = 0.65 (2006) to d = 0.15 to 0.35 after bias correction (2024). Gamification shows a documented novelty decay after about four weeks, and productivity apps retain roughly 9 to 10% of users at day 30 at best. The honest read: a concrete first step helps a little and reliably; progress bars and badges help briefly.

### Cited Findings
- Implementation intentions meta-analysis, 94 tests: d = 0.65 on goal attainment, with benefits for "starting goal work" among others — [Gollwitzer and Sheeran 2006, summarized at NCI](https://cancercontrol.cancer.gov/brp/constructs/implementation_intentions/goal_intent_attain.pdf)
- Updated meta-analysis of 642 tests (Sheeran, Listrom, Gollwitzer, European Review of Social Psychology 2025): trim-and-fill d = 0.35, robust Bayesian d = 0.15 (95% CI 0.08 to 0.22) — [University of Konstanz repository](https://kops.uni-konstanz.de/handle/123456789/69905) (figures via a secondary summary; original not read)
- Mental contrasting with implementation intentions, 21 studies: g = 0.336 for goal attainment, possibly inflated by publication bias — [Frontiers in Psychology 2021](https://www.frontiersin.org/journals/psychology/articles/10.3389/fpsyg.2021.565202/full)
- A two-minute guided reflection on a procrastinated task improved mood, reduced emotional resistance and raised reported likelihood of acting the next day versus controls (BMC Psychology; UCSB). The same team's unpublished follow-up suggests breaking the task down alone gave a small motivation boost and pairing it with a small reward gave a significantly larger one — [University of California news](https://www.universityofcalifornia.edu/news/two-minute-fix-procrastination). Unpublished follow-up: design and n unverified.
- Survey of 202 BBA students: "simplified task breakdowns, task prioritization, and AI-generated summaries" rated the most beneficial AI features. Self-report, not completion data — [Libri 2025](https://www.degruyterbrill.com/document/doi/10.1515/libri-2025-0093/pdf)
- Gamification novelty effect: in a 14-week course, "the gamification's effect started to decrease after four weeks, a decrease that lasted between two to six weeks", followed by a familiarization effect — [Rodrigues et al., Durham repository](https://durham-repository.worktribe.com/OutputFile/1203232)
- Vendor data (NP Digital, 7 clients): progress bars raised retention from 35% to 48%; no control for novelty, not peer reviewed — [Neil Patel](https://neilpatel.com/marketing-stats/gamification-impact-on-retention/)
- Retention baselines: productivity apps about 32 to 33% day 1, 24 to 25% day 7, 9 to 10% day 30, the highest-retaining category; cross-industry about 25 to 26% day 1, 11 to 13% day 7, 5 to 7% day 30 — [Plotline, Nov 2025](https://www.plotline.so/blog/retention-rates-mobile-apps-by-industry); [Phiture](https://phiture.com/mobilegrowthstack/managing-retention-rate-benchmarks-and-expectations/). Another source gives productivity 10 to 18% without specifying the day — [getstream](https://getstream.io/blog/app-retention-guide). Definitions differ (classic vs rolling retention).
- Temporal discounting predicts real-world procrastination; the literature commonly uses task completion time as the single endpoint — [PMC 2024](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC11199680/)

### Inferences
- The mechanism with evidence is not "AI wrote my plan" but "I named a concrete first action and when I will do it". A hand-typed first segment with a start time is an implementation intention; an AI-generated ten-step plan the user did not write is not, and may reduce ownership. Design the AI as a suggester of one next segment, not an author of the whole plan.
- Knowledge, verify: the "unpacking" literature (Kruger and Evans 2004, "If you don't want to be late, enumerate") finds that breaking a task into subtasks makes time estimates longer and more accurate, which cuts against the planning fallacy. That is a defensible reason to show "this looks like 3 to 4 sessions" rather than letting users book one heroic 4-hour block.
- Given a 9 to 10% day-30 ceiling for the best productivity apps, a closed beta of friends will not produce retention statistics that distinguish features. The council should pick features for cost and robustness, then measure "did the user start a block within 60 s of opening the app" and "did a multi-day plan get a second session", not retention.
- Progress UI should avoid the things that decay: streaks and badges are already banned; a progress bar on a specific plan (finite, ends when the task ends) is different from a lifetime score and does not create the novelty-then-shame curve.

### Gaps
- No RCT or credible product postmortem on AI task breakdown and completion. Nothing found from Todoist, Notion, Motion, Reclaim or similar on measured outcomes of their AI planning features.
- The 2024 implementation-intentions figures were taken from a secondary summary; the paper was not read.
- No study of "split a multi-hour task across days" specifically in a student timer context.

## Risks the council must not ignore (ranked)

1. **Push is not a timer.** iOS push needs an installed PWA on iOS 16.4+ (18.4+ for the declarative path), has no action buttons in practice, and Android can defer even high-urgency pushes in Doze. If any block boundary depends on a push arriving, it will miss. Boundaries must be enforced client-side from `startedAt + duration` with server-corrected time; push is a courtesy.
2. **The install step is the funnel.** Without Home Screen install on iOS there is no push, no badge, no standalone and (probably) a separate storage origin from Safari. Every reminder and intercept feature is gated on a manual share-sheet flow most students have never done. Measure install rate before investing further in notification features.
3. **Multi-day plans are a new kind of stored personal data.** Task titles and free-text descriptions of coursework, plus optional transmission to a third-party API with 30-day default retention, are a step up from "started a 45-minute block at 14:02". Privacy inventory, opt-in per request, client-side scrubbing and storing only user-edited output are the minimum. ZDR is by sales arrangement and structured outputs partly override it.
4. **Actions are at-most-once and never retried.** Every Claude call and every push send must follow mutation -> scheduled internal action -> result mutation with an idempotency/version check, or the beta will see duplicate pushes and lost breakdowns on the first transient error.
5. **Free-tier concurrency of 8 scheduled jobs.** Fine for scattered solo blocks; a shared-room "everyone starts at 7" feature or a slow Node push action turns it into a multi-second delay. Keep boundary mutations tiny and know when to move to Professional (256).
6. **Offline negotiation loss.** Buffered mutations live in memory; iOS can kill the PWA before wifi returns. Combined with no Background Sync on iOS, a negotiation made in a lecture-hall dead zone can vanish. Idempotent, versioned deal mutations and a visible "not saved yet" state are needed.
7. **iOS Shortcuts intercept is a hobbyist feature.** Mandatory banners, intermittent prompting, two-minute post-boot blackout, loop risk with no PWA-side fix, and likely landing in Safari rather than the installed app. Ship it as an opt-in power-user recipe with a debug page, never as onboarding.
8. **AI breakdown may harm the core mechanic.** The evidence favors the user naming one concrete next step, not receiving a ten-step plan. A chatty, slow (2 to 5 s plus), occasionally wrong breakdown placed before the Start button adds friction to the one thing Pomodeal is good at. Thinking tokens on Sonnet 5.5 can also silently double output cost; use Haiku 5.5 at low effort and keep the schema tiny.
9. **No retention signal will come from the beta.** With best-in-class day-30 at about 9 to 10% and a friends-only cohort, the council cannot A/B its way to the answer. Choose by cost and robustness and instrument "time to first block" instead.
10. **Platform facts have a short half-life.** Several claims found today conflict (iOS EU PWAs, 7-day eviction, notification actions). Re-verify on a real iPhone on the current iOS before writing specs that depend on them.

## Cheap, robust ideas (high value per engineering week on this stack)

1. **"One block, then decide" as the default breakdown.** Any big task becomes a first block of the user's current preset (30/45/60) plus a stored `remainingEstimateMin`. No AI, no schema, no new runtime. Reuses the existing deal ticket; the only new field is the task title and estimate (privacy inventory: two fields). Captures the implementation-intention effect that actually has evidence.
2. **Versioned scheduler pattern in `packages/core` and `convex/`.** `{blockId, version}` on every scheduled boundary, no-op if stale. One day of work, removes a whole class of double-fire and cancel-race bugs before push lands, and is test-first friendly because the version check is pure.
3. **Server-offset clock.** The start mutation returns `serverNow`; the client stores the offset and renders from corrected time. Half a day. Makes the ring, the scheduled function and the push agree.
4. **Declarative Web Push payload from day one.** Send the `web_push` + `notification` + `navigate` + `app_badge` JSON shape; older browsers fall through to the service worker. One payload format, badge for free on iOS 18.4+, no silent-push penalties. Pair with an install-state check that hides the "Remind me" toggle when `display-mode` is not standalone on iOS.
5. **Segment ledger with a "next due" field, swept by one off-peak daily cron.** A plan is a document with `segments[]` and `nextDueAt`; a single `crons.daily` at an off-peak minute finds due plans and schedules one push action each. Zero per-user crons, a few hundred function calls a month, and "pick up where you left off" tomorrow is a query the client already has cached.
6. **Hand-typed "next segment" prompt at block end instead of AI.** When a block ends on a plan, the stamp screen asks for one line: "Next time, start with ...". Stored on the plan, shown on the next open. This is the cheapest implementation intention and needs no external call.
7. **Optional AI "suggest a first segment" behind a per-user token bucket.** Haiku 5.5, structured output with a tiny schema (`{segments: [{title, minutes}]}` capped at 6), `@convex-dev/rate-limiter` at 10/day per user plus a global cap, scrub emails/names client-side, store only what the user accepts. Expected cost well under $10 a month for the entire beta; the mutation -> scheduled action -> result mutation shape is already required by idea 2.
8. **Wake lock on the active ring (iOS 18.4+ installed, Android).** `navigator.wakeLock.request('screen')` on focus start, release on break, re-request on `visibilitychange`. A dozen lines, and it fixes "my phone locked and I lost the ring" without any backend work.
9. **Unsaved-deal indicator and idempotent negotiation.** Client-generated `dealId`, a small "saving" state on the ticket until the mutation confirms, and server-side dedupe on `dealId`. Covers campus-wifi drops and the in-memory buffer limitation with no new infrastructure.
10. **Intercept as a documented recipe, not a feature.** Publish a one-page `/intercept` setup guide and a Convex HTTP action that accepts a per-user token POST and records `interceptedAt`; the shortcut then opens `pomodeal.app/start`. Ship with a debug view showing the last three intercepts received so users can self-diagnose Shortcuts failures. Days of work, no promise of reliability, and it stops Shortcuts from blocking the roadmap.
